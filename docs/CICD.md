# دليل البايب لاين — CI/CD

> مرجع عملي لبايب لاين منصة فطن، ومنهج قابل للنقل إلى أي مشروع آخر.

---

## 1. الفكرة الأساسية

البايب لاين ليس مجموعة سكربتات — هو **عقد آلي** يجيب على سؤال واحد:

> هل هذا التغيير آمن ليصل إلى المستخدم؟

كل مرحلة تجيب على جزء من السؤال، وكل واحدة **بوابة** لها قرار: يمر أو يتوقف.

### قاعدة التكلفة (لماذا كل هذا؟)

| أين اكتُشف الخطأ      | التكلفة النسبية          |
| --------------------- | ------------------------ |
| أثناء الكتابة (IDE)   | 1×                       |
| خطاف Git (pre-commit) | 5×                       |
| CI على الـ PR         | 10×                      |
| بيئة الاختبار         | 50×                      |
| **الإنتاج**           | **100× — وأحياناً سمعة** |

كل مرحلة نضيفها تنقل الاكتشاف يساراً على هذا الجدول. هذا هو **Shift Left**.

## 2. البنية

```
المطوّر
  │
  ├─ pre-commit ──► أسرار + تنسيق + lint على الملفات المرحّلة   (~15 ثانية)
  ├─ commit-msg ──► صيغة Conventional Commits                    (~2 ثانية)
  ├─ pre-push  ──► typecheck + اختبارات الوحدة                   (~60 ثانية)
  │
  ▼
Pull Request
  │
  ├── CI (ci.yml) ─────────────────────────────────────┐
  │     🔍 الجودة الثابتة   typecheck + eslint + prettier
  │     🧪 اختبارات الوحدة  vitest + تغطية
  │     📦 البناء           vite + ميزانية حجم
  │     🎭 E2E              playwright (chromium + firefox)
  │     📊 SonarQube        بوابة جودة (service container)
  │     ✅ بوابة CI         ← تُربط بحماية الفرع
  │                                                     │
  ├── Security (security.yml) ─────────────────────────┤
  │     🔐 Gitleaks         أسرار
  │     📦 SCA              npm audit + OSV + Snyk
  │     🔎 Semgrep          SAST
  │     🔗 Trivy + SBOM     سلسلة التوريد
  │     🛡️ بوابة الأمن      ← تُربط بحماية الفرع
  │                                                     │
  └── CD (cd.yml) ─────────────────────────────────────┘
        🔍 Deploy Preview   رابط مؤقت + دخان
        🚀 الإنتاج          بموافقة يدوية + دخان + تراجع
```

**زمن التنفيذ الفعلي:** ~3 دقائق (بالتوازي). تسلسلياً كان سيستغرق ~7.

## 3. الأوامر

```bash
npm run dev              # خادم التطوير
npm run build            # بناء الإنتاج
npm run preview          # معاينة البناء على 4173

npm run typecheck        # فحص أنواع TypeScript — بوابة صارمة (0 أخطاء)
npm run lint             # ESLint بسقف 254 تحذيراً
npm run lint:fix         # إصلاح تلقائي
npm run format           # Prettier — كتابة
npm run format:check     # Prettier — فحص فقط (يُستخدم في CI)

npm run test             # اختبارات الوحدة
npm run test:watch       # وضع المراقبة أثناء التطوير
npm run test:ui          # واجهة رسومية للاختبارات
npm run test:coverage    # مع تقرير التغطية
npm run test:e2e         # Playwright
npm run test:e2e:ui      # Playwright بواجهة تفاعلية

npm run audit:deps       # فحص ثغرات التبعيات
npm run sbom             # توليد قائمة المكوّنات (CycloneDX)

npm run sonar            # تحليل SonarQube + بوابة الجودة
npm run sonar:up         # تشغيل SonarQube محلياً (Docker)
npm run sonar:down       # إيقافه

npm run validate         # كل ما سبق — نفس ما يشغّله CI
```

## 4. القرارات الهندسية وأسبابها

### 4.1 فصل `typecheck` عن `build`

`vite build` **لا يفحص الأنواع** — يحذفها فقط (transpile-only). أُثبت ذلك عملياً:
كود فيه `error TS2322` صريح **نجح بناؤه** وفشل في `typecheck` فقط.

> القاعدة: «البناء نجح» ≠ «الكود سليم». `typecheck` مرحلة إلزامية مستقلة.

### 4.2 استراتيجية السقف المتناقص (Ratchet)

المشروع بدأ بـ 171 خطأ ESLint و 46 خطأ TypeScript. ثلاثة مسارات كانت متاحة:

| المسار            | النتيجة                                                 |
| ----------------- | ------------------------------------------------------- |
| بوابة صارمة فوراً | كل PR يفشل → الفريق يتجاوز البايب لاين بـ `--no-verify` |
| تعطيل القواعد     | بايب لاين أخضر لا يفحص شيئاً — أمان وهمي                |
| **Ratchet** ✅    | نقبل الدين الحالي كسقف، ونمنع أي زيادة عليه             |

**التطبيق:**

- `typecheck`: صفر أخطاء (فُصلت «المتغيرات غير المستخدمة» إلى ESLint)
- `lint`: `--max-warnings 254` — **هذا الرقم يَنقص فقط، لا يزيد أبداً**
- التغطية: عتبات مبنية على القياس الفعلي (2.3%)، **ترتفع فقط**
- SonarQube: `sonar.newCode.referenceBranch=main` — الكود الجديد فقط

هذه بالضبط فلسفة SonarQube الرسمية: **Clean as You Code**.

### 4.3 ابنِ مرة واحدة، انشر نفس القطعة

كل بيئة تبني نسختها = «يشتغل عندي وما يشتغل عندك». القطعة (`dist`) تُبنى مرة
واحدة وتُرفع كـ artifact، ثم تُنزَّل كما هي في E2E والنشر.

**درس عملي:** أول تشغيل فشل لأن Playwright أعاد البناء داخل job الاختبارات
بدون الأسرار المتاحة في job البناء → التطبيق انهار بشاشة بيضاء وفشلت 7 من 9
اختبارات. الإصلاح: خدمة `dist` المنزَّلة مباشرة في CI.

### 4.4 سياسة الثغرات حسب النطاق

| النطاق         | السياسة                              | السبب                              |
| -------------- | ------------------------------------ | ---------------------------------- |
| تبعيات الإنتاج | حرجة = 0، عالية = 0 → **تحجب الدمج** | تصل إلى متصفح المستخدم             |
| تبعيات التطوير | تقرير + Dependabot                   | لا تُشحن؛ خطرها على الـ runner فقط |

عند القياس: 7 حرجة + 20 عالية إجمالاً — **كلها في أدوات التطوير**. الإنتاج كان
فيه 4 عالية حقيقية (Open Redirect و XSS في `react-router-dom`) وأُصلحت.

### 4.5 CI لا يحتاج أسرار الإنتاج

هدف CI هو التحقق من أن الكود **يُبنى ويعمل** — لا الاتصال بقاعدة بيانات حقيقية.
لذا يبني CI بقيم نائبة، والأسرار الحقيقية تُستخدم في CD فقط.

```yaml
VITE_SUPABASE_URL: ${{ secrets.VITE_SUPABASE_URL || 'https://ci-placeholder.supabase.co' }}
```

**السبب العملي:** PRs من Dependabot و forks **لا تصلها أسرار المستودع** —
حماية مقصودة من GitHub: Dependabot يجلب `package.json` معدّلاً من الإنترنت،
فلو حصل على أسرارك أمكن لحزمة npm خبيثة سرقتها عبر `postinstall`.

**أُثبت عملياً:** أول ثلاث PRs من Dependabot فشلت جميعها بنفس النمط (شاشة
بيضاء في E2E) لهذا السبب بالضبط.

**السبب الأمني:** إن لم يكن للـ workflow وصول إلى أسرار، فلا يوجد ما يُسرَّب
لو اختُرق سطر فيه.

### 4.6 بوابة نهائية واحدة

حماية الفرع تتطلب أسماء فحوصات ثابتة. لو رُبط كل job على حدة، فإضافة job جديد
تعني تعديل الإعدادات يدوياً. لذا كل الـ jobs تصبّ في `ci-gate` واحد.

```yaml
ci-gate:
  needs: [quality, test, build, e2e, sonarqube]
  if: always() # ← حرجة!
```

> **فخ شائع:** بدون `if: always()` يُتخطّى الـ job عند فشل أي تابع، فيظهر
> بحالة `skipped` — وحماية الفرع **تعتبر skipped نجاحاً**. أي أن غياب هذا
> السطر يجعل الحماية بلا قيمة.

### 4.7 الخطافات مساعدة لا بديل

الخطافات تُمسك الخطأ في ثوانٍ، لكن `--no-verify` يتجاوزها دائماً.
**أُثبت عملياً:** كود مكسور دُفع بتجاوز الخطافين، فأمسكه CI بالكامل.

> الخطافات = راحة المطوّر. CI = الضمانة.

## 5. SonarQube

### محلياً

```bash
npm run sonar:up      # يشغّل SonarQube + PostgreSQL
# انتظر ~2 دقيقة، ثم افتح http://localhost:9000  (admin / admin)
npm run test:coverage
npm run sonar         # تحليل + بوابة جودة
npm run sonar:down
```

### في CI

يعمل كـ **Service Container** — سيرفر مؤقت يولد ويموت مع الـ job:

```yaml
services:
  sonarqube:
    image: sonarqube:10.7.0-community
    ports: ['9000:9000']
    env:
      SONAR_ES_BOOTSTRAP_CHECKS_DISABLE: 'true'
```

`scripts/sonar.mjs` يتولى: انتظار الجاهزية → تغيير كلمة المرور الافتراضية →
توليد توكن → التحليل → استطلاع بوابة الجودة.

## 6. الأسرار

| السر                     | لماذا                   |
| ------------------------ | ----------------------- |
| `VITE_SUPABASE_URL`      | البناء                  |
| `VITE_SUPABASE_ANON_KEY` | البناء                  |
| `VITE_OPENAI_API_KEY`    | البناء                  |
| `VITE_N8N_WEBHOOK_URL`   | البناء                  |
| `NETLIFY_AUTH_TOKEN`     | النشر (غير مضبوط بعد)   |
| `NETLIFY_SITE_ID`        | النشر (غير مضبوط بعد)   |
| `SNYK_TOKEN`             | اختياري — فحص SCA إضافي |

```bash
gh secret set NETLIFY_AUTH_TOKEN --repo Hashim0011/Faten_Platform
```

**قواعد:**

1. لا تُرسل سراً عبر شات أو إيميل — يُعتبر مكشوفاً فور مروره بقناة غير آمنة
2. `.env` لا يدخل Git أبداً (`.gitignore` + Gitleaks + خطاف pre-commit)
3. عند التسريب: **إلغاء المفتاح أولاً**، ثم تنظيف التاريخ — لا العكس

### دين أمني معروف

تاريخ المستودع يحتوي `.env` بمفاتيح حقيقية (commit `0a5fc39`). المستودع خاص
حالياً فالخطر محدود. **قبل أي تحويل إلى public**: إلغاء مفاتيح OpenAI و Gemini.

## 7. حماية الفرع

تتطلب مستودعاً عاماً أو خطة GitHub Pro. القاعدة جاهزة في
`.github/branch-protection.json`:

```bash
gh api -X POST repos/Hashim0011/Faten_Platform/rulesets \
  --input .github/branch-protection.json
```

تفرض: لا دفع مباشر على `main` • لا force-push • لا حذف •
`✅ بوابة CI` و `🛡️ بوابة الأمن` خضراوان.

## 8. الأخطاء التي واجهناها فعلياً

| الخطأ                                                | السبب                                  | الدرس                                                                          |
| ---------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------ |
| `refusing to allow a PAT ... without workflow scope` | التوكن بلا صلاحية `workflow`           | GitHub يفصل صلاحية تعديل الـ workflows لأن من يعدّلها ينفّذ أي كود على runnerك |
| `Unable to resolve action trivy-action@0.28.0`       | الوسم `v0.28.0` ببادئة `v`             | تحقّق من الوسم الفعلي؛ الأأمن التثبيت على SHA كامل                             |
| Prettier ينجح محلياً ويفشل في CI                     | commit بـ `--no-verify`                | CI هو الحكم، لا الخطافات                                                       |
| 7 من 9 اختبارات E2E تفشل                             | إعادة بناء بلا أسرار                   | ابنِ مرة واحدة وانشر نفس القطعة                                                |
| `lint-staged` يعلّق دقائق على ويندوز                 | تعارض مع typescript-eslint             | استُبدل بسكربت مباشر: أسرع وأوضح                                               |
| `npm audit fix --omit=dev` يحذف devDeps              | `--omit` يؤثر على التثبيت لا الفحص فقط | استخدمه مع `audit` فقط، لا مع `audit fix`                                      |
